# 从 agentsview 吸收会话查看能力的改进指导

## 面向对象

本文提供给 `codex-session-renderer` 负责人，用于判断可以从
`agentsview` 吸收哪些成熟能力，以及这些能力迁入后要让用户获得什么体验。

本文按用户能感受到的功能意图组织，用于帮助负责人安排产品改进顺序、验收标
准和交付边界。

## 总体方向

`codex-session-renderer` 适合保持轻量，继续专注于 Codex 会话查看、复盘和
远程快照浏览。`agentsview` 的价值在于它已经处理过很多真实会话中的特殊情
况，可以把这些经验迁成更准确、更清楚的显示能力。

建议迁移的重点是把已经验证过的判断规则、展示习惯和样例沉淀到当前项目中。
迁入后，用户打开一个 Codex 会话时，应当更容易回答这些问题：

- 这次会话到底发生了什么？
- 用户什么时候提了什么要求？
- Codex 做了哪些操作？
- 哪些操作成功了，哪些操作失败了？
- 是否派出子任务，子任务做到了什么程度？
- 这次会话是完成了、中断了，还是还在等待后续输入？
- 导出的记录是否完整支撑复盘和交接？

## 第一阶段：先保证会话显示准确

### 1. 去除重复显示的旧内容

有些 Codex 会话会把旧会话内容带到新会话开头。用户看到这种会话时，容易以
为同一段对话又发生了一遍，也可能误判实际工作量。

迁入后的功能意图：

- 新会话只突出真正新增的内容。
- 旧会话被带入时，页面能识别并压住重复部分。
- 会话统计、时间线和导出内容都以真实发生的新内容为准。

验收方式：

- 准备一个“新会话开头包含旧会话内容”的样例。
- 页面中不重复展示旧会话的主体内容。
- 统计中的消息数和操作数不把旧内容重复算入。

### 2. 正确展示中断、继续和未完成

真实使用中，Codex 会话经常会被用户打断、继续，或停在某个操作之后等待下一
步。当前项目需要把这些状态展示得更清楚。

迁入后的功能意图：

- 用户能看出会话是完成、中断，还是仍在等待。
- 中断后被重复写入的首条用户请求只展示一次。
- 会话列表里可以用清楚的状态提示帮助用户筛选。

验收方式：

- 准备已完成、中断、未完成三类样例。
- 会话详情和会话列表显示的状态一致。
- 中断后继续的会话，用户请求不重复干扰阅读。

### 3. 标题改名及时生效

Codex 会话标题可能在会话结束后被修改。用户回头查找历史时，标题是最重要的
入口之一。

迁入后的功能意图：

- Codex 改过标题后，列表展示新标题。
- 远程快照带回标题信息后，本地页面能跟着更新。
- 标题缺失时，再用首条有效用户请求或文件名兜底。

验收方式：

- 准备同一个会话文件加不同标题记录的样例。
- 页面刷新后显示新标题。
- 标题记录缺失时，仍然有可读的默认标题。

### 4. 会话文件位置识别更稳定

Codex 会话可能存在不同目录形态，包括按日期分目录和归档目录。用户关心的是
稳定找到会话，文件位置由页面自动处理。

迁入后的功能意图：

- 正常会话和归档会话都能被发现。
- 同一个会话同时出现在多个位置时，页面选择更合适的一份展示。
- 文件路径变化时，历史入口尽量保持可用。

验收方式：

- 准备按日期目录、归档目录、重复会话三类样例。
- 列表不出现明显重复项。
- 打开会话时能命中可读取的最新内容。

## 第二阶段：让会话过程更好读

### 5. 工具操作变成用户看得懂的动作

Codex 会话中大量内容是工具操作。原始内容通常像参数包，业务负责人和普通用
户很难快速判断它在做什么。

迁入后的功能意图：

- 读文件显示为“读取某个文件”。
- 改文件显示为“修改某个文件”和大致改动量。
- 写文件显示为“写入某个文件”和新增内容规模。
- 搜索显示为“搜索某个关键词”和命中数量。
- 运行命令显示为“运行某条命令”和执行结果。
- 应用补丁显示为“修改了哪些文件、增删多少行”。

验收方式：

- 同一组工具操作在详情页、时间线、审计视图和导出中名称一致。
- 常见操作不再只显示原始参数。
- 展开后仍然能看到完整原始内容，方便排查。

### 6. 工具输出突出结果

工具输出往往很长。用户最先需要知道的是成功、失败、命中了什么、改了什么，
然后才是完整输出。

迁入后的功能意图：

- 测试输出能显示通过、失败、数量等摘要。
- 搜索输出能按文件和行号组织。
- Git 状态能显示哪些文件变了。
- 普通长输出先给摘要，再允许展开查看全部。

验收方式：

- `npm test`、`node --test`、`rg`、`git status`、`apply_patch` 等常见输出
  有清楚摘要。
- 失败输出有醒目的失败提示。
- 长输出不会把主阅读区完全淹没。

### 7. 隐藏机器自动塞入的上下文

很多会话开头会包含环境信息、内部状态、历史恢复内容。这些内容对排查有用，
但默认阅读时会干扰主线。

迁入后的功能意图：

- 默认阅读视图只展示用户真实请求和 Codex 有意义的回复。
- 内部上下文可在原始视图中查看。
- 搜索和导出可以选择是否包含这类内容。

验收方式：

- 包含环境信息、内部状态、历史恢复内容的样例，在默认视图中保持清爽。
- 原始视图仍能找到完整记录。
- 导出时提供清楚的取舍方式。

### 8. 思考摘要和图片附件显示得更安全

Codex 会话可能包含加密思考内容、思考摘要、图片或大段内联数据。默认视图要
让用户知道这些内容存在，同时控制体积和敏感内容暴露。

迁入后的功能意图：

- 有明文思考摘要时展示摘要。
- 只有加密内容时展示“有加密思考内容”，不把加密串塞进主界面。
- 图片以附件摘要展示，内联大数据默认压缩成提示。
- 搜索结果不被大段图片数据污染。

验收方式：

- 图片型会话仍能看出用户上传了图片。
- 加密思考内容不会进入普通搜索文本。
- 原始视图仍保留完整排查入口。

## 第三阶段：把子任务关系讲清楚

### 9. 主任务和子任务能串起来

Codex 会把一部分工作派给子任务。用户复盘时，不只想知道子任务存在，还想知
道它是由哪个操作派出的、最终返回了什么。

迁入后的功能意图：

- 主会话中能看到“这里派出了子任务”。
- 子任务节点能展示状态：进行中、完成、失败。
- 子任务结果能回挂到对应的主会话操作上。
- 点击子任务可以打开完整子会话。

验收方式：

- 一个包含子任务的样例，主会话和子会话能互相跳转。
- 子任务结果不散落成普通用户消息。
- 子任务失败时，主会话中能看出失败来源。

### 10. 时间线能表达工作推进

目标项目已有时间线和追踪视图，可以进一步让它服务复盘，呈现清楚的工作推进
过程。

迁入后的功能意图：

- 每一轮用户请求、Codex 回复、工具操作、子任务都有清楚顺序。
- 用户能快速跳到失败、验证、最终回复等关键节点。
- 会话很长时，先看摘要也能知道大概过程。

验收方式：

- 长会话能在几秒内看出主线。
- 点击关键节点能定位到原始内容。
- 时间线和正文视图中的同一件事名称一致。

## 第四阶段：让导出更适合复盘和交接

### 11. 导出记录保留关键证据

简单聊天导出适合阅读，但复盘和交接需要保留更多结构化信息。

迁入后的功能意图：

- 导出内容包含用户请求、Codex 回复、工具操作、工具结果。
- 子任务关系能在导出中保留。
- 思考摘要、代码块、文件修改、命令输出分区清楚。
- 导出文件适合发给其他人复盘，也适合后续再导入分析。

验收方式：

- 对同一个复杂会话，导出后能看出完整工作链路。
- 子任务不会在导出中丢失。
- 工具参数和结果可读，同时保留必要原始信息。

### 12. 提供两种导出口径

不同用户的导出需求不同。日常分享需要短，审计复盘需要完整。

迁入后的功能意图：

- 简洁导出：突出对话和最终结果。
- 完整导出：保留操作、输出、子任务和原始线索。

验收方式：

- 页面提供清楚选择。
- 两种导出都能稳定生成。
- 文件名包含会话标题和时间，便于保存。

## 第五阶段：用真实样例守住质量

### 13. 建立特殊场景样例库

`agentsview` 的价值之一是积累了很多真实边界情况。迁移时应优先把样例带过来，
让目标项目每次改动都能自动校验。

建议纳入的样例：

- 新会话开头带旧会话内容。
- 用户中断后继续。
- 标题后来被改名。
- 会话存在归档副本。
- 主会话派出子任务。
- 子任务完成、失败、仍在运行。
- 工具输出很长。
- 工具输出包含失败。
- 会话包含图片。
- 会话包含加密思考内容。

验收方式：

- 每个样例都有明确期待结果。
- 每次改动后自动检查这些样例。
- 样例说明用业务语言描述，不只描述字段。

## 优先级建议

### P0：先做准确性

- 去除重复显示的旧内容。
- 正确展示完成、中断、未完成。
- 标题改名及时更新。
- 正常会话和归档会话稳定识别。

这些能力影响用户是否信任页面显示结果，优先处理。

### P1：再做可读性

- 工具操作摘要。
- 工具输出摘要。
- 默认隐藏内部上下文。
- 思考摘要和图片附件安全展示。

这些能力影响用户阅读效率，适合在准确性稳定后推进。

### P2：增强复盘能力

- 主任务和子任务串联。
- 时间线关键节点跳转。
- 完整导出。
- 特殊场景样例库。

这些能力让项目从“能看会话”升级为“能复盘工作”。

## 不建议迁入的内容

以下内容会把当前项目变重，和 Codex 专用会话查看工具的定位不匹配：

- 多种 AI 工具的统一管理。
- 成本、价格、用量大盘。
- 长期数据库归档系统。
- 完整后台同步服务。
- 大型前端框架迁移。
- 多用户权限和团队管理。

这些能力可以作为远期扩展方向，但当前阶段应集中做好 Codex 会话本身的准确
展示、清晰阅读和可靠导出。

## 负责人可采用的推进方式

建议按“小步吸收、样例验证、界面跟进”的方式推进：

1. 先选一个真实问题，例如“会话内容重复”。
2. 准备一份最小样例，写清楚用户应该看到什么。
3. 加入判断规则，让页面显示符合预期。
4. 再把同一规则应用到列表、详情、时间线和导出。
5. 最后补充文档说明这类会话会如何展示。

每次只解决一类用户可感知的问题，迁移风险最低，也方便负责人检查成果。

## 最终目标

迁移完成后，`codex-session-renderer` 应该保持轻量，但在真实 Codex 会话面前
更可靠：

- 列表里找得到正确会话。
- 打开后看得到真实主线。
- 工具操作能被读懂。
- 子任务关系能追踪。
- 中断、失败和完成状态清楚。
- 导出内容能支持复盘。

这类改进的核心价值是提升信任感：用户相信页面显示的是一次 Codex 工作的真
实过程，并且能用它回看、解释和交接。

## 负责人评审结论（2026-07-07）

### 核验范围

本次核验了 `agentsview` 仓库当前 `main` 的源码，提交为
`4a5cca97b0b22a8b98a96899aa19390858f5fc01`。核验重点是 Codex 解析器、会
话列表、工具展示、子代理展示、导出和测试样例。

总体判断：这份指南的大方向成立，但不能理解成“agentsview 的能力全部都要迁
入”。`agentsview` 是多 AI agent、SQLite/DuckDB/PostgreSQL、成本统计和同步
平台；本项目仍应保持 Codex 专用、只读、轻量会话工作台。真正值得吸收的是它
处理 Codex 边界数据的规则和回归样例。

### 逐项判断

1. 去除重复显示的旧内容：确实存在，值得做。
   `agentsview` 的 Codex 解析器有 `forkGate`，专门压掉 fork 会话开头重放的
   父会话历史，避免消息和 token 被重复计算。本项目当前没有等价的 fork
   replay gate，只做了同一 turn 内的普通重复消息去重。建议列为 P0。

2. 正确展示中断、继续和未完成：确实存在，值得做。
   `agentsview` 读取 `task_started`、`task_complete`、`turn_aborted` 来判断
   termination status，并且对 `turn_aborted` 后 Codex 重新写入首条用户请求
   的情况做了去重。本项目当前能处理 `task_started`、`task_complete` 和
   `task_failed`，但没有把 `turn_aborted` 作为中断状态，也没有完整的续跑首
   prompt 去重。建议列为 P0。

3. 标题改名及时生效：存在，但本项目已经大体具备。
   `agentsview` 读取 `session_index.jsonl` 的 `thread_name`，并把
   `session_index.jsonl` 的 mtime 纳入会话 fingerprint，让重命名触发重解析。
   本项目优先读取 `state_5.sqlite` 的 `threads.title`，SQLite 不可用时也会
   读取 `session_index.jsonl`。后续只需要补“远程快照标题更新”和缓存失效测
   试，不应作为大功能重做。

4. 会话文件位置识别更稳定：确实存在，值得补齐。
   `agentsview` 同时识别日期目录和 `archived_sessions` 平铺目录，并按 UUID
   对 live 和 archived 副本去重。本项目在 SQLite 可用时依赖
   `threads.rollout_path`，但无 SQLite 回退扫描只扫 `.codex/sessions`，没有
   覆盖 `.codex/archived_sessions`。建议列为 P1；如果远程快照经常缺
   `state_5.sqlite`，则提升到 P0。

5. 工具操作变成用户看得懂的动作：存在，但本项目已有较多实现。
   `agentsview` 有结构化 tool summary，覆盖 Bash、Read、Edit、Write、Grep、
   Glob、Task 等；本项目的 `public/tool-summary.js` 已经覆盖 Codex
   `exec_command`、`apply_patch`、`tool_search` 等，并且支持自定义规则。建
   议只做差距补齐和样例测试，不迁移整套实现。

6. 工具输出突出结果：存在，但本项目不弱于对方。
   `agentsview` 的工具输出主要是折叠、预览和结果历史；本项目已经有
   `git status`、搜索命中、验证输出和 `apply_patch` 的结构化 viewer。建议继
   续沿当前实现扩展，不作为 agentsview 迁入项。

7. 隐藏机器自动塞入的上下文：确实存在，值得继续做。
   `agentsview` 会把 `AGENTS.md`、`environment_context`、`turn_aborted`、
   goal context、subagent notification 等识别为系统内容，不计入用户消息。
   本项目精简视图已经清理部分 AGENTS/环境上下文，但 `buildTurns`、Markdown
   导出和部分搜索路径仍可能保留这些内容。建议列为 P0.5。

8. 思考摘要和图片附件显示得更安全：存在，本项目已经具备核心能力。
   `agentsview` 有 ThinkingBlock 和多 provider thinking 解析；本项目已经对
   encrypted reasoning 做脱敏，对 data URI 图片只保留附件摘要并从搜索文本
   中移除原始大数据。后续更值得做的是在精简视图里把图片附件和加密 reasoning
   的存在感展示得更清楚，优先级 P2。

9. 主任务和子任务能串起来：确实存在，本项目也已有基础。
   `agentsview` 在 tool call 上挂 `subagent_session_id`，前端可 inline 展开子
   会话。本项目通过 `thread_spawn_edges`、`spawn_agent` 和
   `subagent_notification` 构建 Trace/Compact/Audit，并支持打开子会话。差距
   主要是 SQLite 不可用时的 fallback、子代理状态文案和导出深度，建议 P2。

10. 时间线能表达工作推进：存在，但不是当前最大短板。
    `agentsview` 有 call timing、running duration、SignalPanel 等。本项目已
    经有 Trace、Audit、Review Dock 和执行聚合，复盘表达比单纯时间线更贴合
    Codex 工作台。建议只做关键节点跳转和失败/验证锚点增强，P2。

11. 导出记录保留关键证据：部分存在，需要校正理解。
    `agentsview session export` 是 raw source 导出；HTTP Markdown/HTML 导出
    支持 `depth=1|all` 带子代理；但 `agentsview export sessions` 是内容外的
    session 摘要和成本数据，不是完整复盘包。本项目已有 Markdown 导出，但还
    缺子代理深度、证据视图口径和导出口径选择。建议 P2。

12. 提供两种导出口径：产品上值得做，但不能说是 agentsview 的直接现成模式。
    `agentsview` 有 raw source、Markdown/HTML、session summary 多种出口，但
    不是“简洁/完整”两档复盘导出。对本项目而言，两档导出符合用户交接场景，
    但应按本项目视图模型设计，优先级 P2。

13. 建立特殊场景样例库：确实值得做，且应提前做。
    `agentsview` 价值很大一部分体现在大量 parser、frontend 和 e2e 回归样例。
    本项目已有不少单元测试，但缺少覆盖 fork replay、`turn_aborted` 续跑、
    archived 副本、无 SQLite 回退、真实子代理完成/失败/运行中的样例库。建议
    作为 P0 支撑项，先建样例再改解析规则。

### 调整后的优先级

P0 先做三件事：

- Codex fork replay / 旧内容重放识别和去重。
- `turn_aborted`、运行中、等待用户输入的状态识别和列表展示。
- 特殊场景样例库，至少覆盖 fork、interrupt/resume、archived、subagent、图
  片和 encrypted reasoning。

P1 做稳定性补齐：

- 无 SQLite 回退时扫描 `archived_sessions`，并对 live/archived 副本去重。
- 默认阅读、Markdown 和搜索路径继续隐藏机器上下文。
- 给现有工具摘要补缺口测试，而不是替换实现。

P2 做复盘体验增强：

- 子代理导出深度和状态展示。
- 关键节点跳转、失败/验证锚点。
- 简洁导出和完整导出两种口径。
- 图片附件、加密 reasoning 在精简视图中的更清楚提示。

暂不建议做：

- 多 agent 统一平台。
- 成本、价格、用量大盘。
- SQLite 归档系统以外的长期数据库平台。
- PostgreSQL、DuckDB、S3、daemon watch 等同步平台能力。
- 大型前端框架迁移。

这些确实是 `agentsview` 的能力，但它们服务的是“跨 agent 归档和分析平台”，
不是当前项目的核心目标。
