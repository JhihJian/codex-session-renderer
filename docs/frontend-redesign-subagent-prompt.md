# 会话证据工作台重构：执行型 Subagent 提示词

将以下提示词交给拥有代码修改权限的执行型 subagent。主 agent 负责协调、评审、验证和最终整合；执行 agent 对每轮实际改动与证据负责。

```text
接下来进行“会话证据工作台”前端重构的持续迭代。

你是本轮工作的执行负责人。请在理解现有代码、测试和真实页面后，自主决定实现顺序、组件边界与视觉细节。你必须直接修改代码、验证结果，并在每一轮之后重新审视尚未解决的高价值问题。不要停留在设计建议或只提交静态分析。

## 项目目标

codex-session-renderer 是一个本地优先、只读的 Codex / Pi Agent 会话浏览、复盘与交接工具。它不是通用 AI 管理平台，也不是营销页。

完成后，开发者或技术负责人应能沿着清楚的路径完成一次会话复盘：

定位会话 -> 先理解本次工作的可交接结论 -> 需要时阅读过程 -> 核对验证与风险 -> 仅在必要时诊断原始事件。

用户应能在短时间内回答：本次要做什么、做到哪里、结果是否可信、证据在哪里、还有什么风险或待继续事项。

## 本轮范围

- 将当前平级的“阅读 / 审计链 / 统计 / 原始事件”重组为以“会话、复盘、诊断”为中心的清晰工作语境；统计和原始事件可以成为诊断语境内的层级，不应与日常阅读争夺首屏。
- 在主内容标题附近建立紧凑、可跳转、基于现有派生数据的交接摘要，优先呈现目标、当前状态、结果或待继续事项、验证、风险/缺口、改动范围和子代理状态。不得通过新增模型调用或伪造数据生成摘要。
- 让左栏只服务于定位会话或任务，中栏承担理解工作主线，右栏成为“当前对象核对”而不是会话结论的唯一入口。
- 建立一套适合高密度工作台的视觉语言。唯一强特征是“证据刻度脊柱”：它在会话列表选中态、会话轮次、复盘节点、原始事件和复核对象之间表达当前路径与证据定位。它必须是结构导航，不是装饰性时间线，也不能只依赖颜色传达含义。
- 在大屏、窄桌面和移动端都让核心阅读任务优先。1281px 以上保留可调三栏；821-1280px 的复核应按需出现，不应默认挤占长文本阅读；820px 以下沿用可访问的会话/内容/复核三面板语义。
- 同步维护与实际变更有关的 README 或设计说明，并在仓库中维护 `docs/frontend-redesign-iteration-log.md`，记录每轮的发现、改动、验证证据、未解决风险与下一步决定。

## 必须保持的边界

- 保持原生 HTML/CSS/JavaScript 技术路线，不引入前端框架或大型 UI 框架。
- 保持本地优先、只读、数据源隔离、受限原始事件读取、快照/取消语义和现有 API 合同。不要为视觉重构改变后端数据归属或放宽安全边界。
- 保持现有键盘操作、真实 tab/panel 语义、焦点迁移、ARIA 公告、窄屏行为和请求过期隔离。若重构交互，必须同时更新对应端到端测试。
- 工具工作台保持中性色为主、紧凑可扫描、边框和圆角克制。不要做营销 hero、卡片墙、渐变背景、装饰球、玻璃拟态、泛 SaaS KPI 大盘或抽象插画。
- 不要把颜色当作唯一语义。失败、验证、选中和角色必须同时有文字、位置、图标或形状线索。所有图标按钮必须有可访问名称和 hover 提示。
- 支持系统浅色/深色模式、可见焦点、`prefers-reduced-motion`；减少动画偏好下不得强制平滑滚动。
- 不要回退已有用户改动。只处理本任务关联文件；遇到并行改动时先读取并适配。

## 设计方向

把界面做成“证据账本”而非卡片堆叠：中性画布、细分隔线、稳定的等宽元信息、舒适正文行高、代码与原始 JSON 独立深色阅读面。交互主色可使用低饱和 teal，红色只表示真实风险或失败；既有角色色降级为内容分类色。

优先复用系统字体和等宽字体。页面不是说明产品如何使用的地方，界面文字必须服务定位、理解、操作或恢复。

## 相关材料

- `public/index.html`、`public/styles.css`、`public/app.js` 是前端核心。
- `README.md` 描述已有数据源、可访问性、响应式和诊断边界。
- `docs/agentsview-improvement-guide.md` 说明产品要帮助用户理解什么。
- `test/e2e/workbench.spec.mjs`、`test/e2e/inspector-resizer-focus.spec.mjs`、`test/e2e/source-response.spec.mjs` 保护布局、断点、焦点和来源隔离。
- 现有 `public/app.js` 已有会话、审计、统计、原始事件与复核投影；优先重新编排和表达已有数据，而不是重复实现数据逻辑。

## 迭代方式

持续按以下循环推进，不以固定轮数为目标：

1. 阅读当前实现、测试和相关文档，使用真实或 fixture 数据启动页面；先识别阻碍“快速得到可信结论”的最高影响差距。
2. 选择一批边界清晰、能带来真实体验改善的改动实施。先完成可用的垂直切片，再扩展到相邻视图；不要一次性重写整个 CSS 文件。
3. 为新增或改变的体验补充有意义的 DOM、ARIA 或几何契约测试，并运行 `npm run verify`。现有 E2E 默认只在失败时保存截图，不能把它当作视觉验收：请使用确定性 fixture，以可复现方式在 `test-results/`（已忽略）输出至少 1440x900、1024x800、390x844 的浅色和深色审阅截图；若项目尚无合适入口，可添加一个不依赖像素基线、专用于捕获审阅图的 Playwright 用例或脚本。浏览器缺失时先运行 `npm run install:e2e-browser`。逐张检查首屏层级、文本截断/换行、无横向溢出、面板可达性、焦点可见性与深色对比度。
4. 审视截图、测试结果和 diff。修复影响用户主任务、可访问性、响应式、数据边界或既有行为的缺陷；把其余问题明确写入迭代日志，并决定是否值得继续。
5. 每轮更新迭代日志，至少写明：本轮问题假设、改动、验证命令和截图位置、结果、剩余风险、下一轮是否继续及原因。

需要独立判断时，可请求只读 subagent 分别从用户流程、视觉密度/可访问性、回归风险角度评审。评审意见必须转化为具体改动、验证动作，或带理由的拒绝，不能只罗列观点。

## 交付质量门槛

只有同时满足以下状态，才可以认为本轮重构完成：

- 默认会话路径先呈现可交接结论，用户能清楚进入过程、复盘和诊断；交接摘要所有信息来自真实已有数据，并能定位到对应内容或诚实显示缺失。
- 会话、复盘、诊断、复核台、任务归档和远端索引的职责及命名一致，不存在两个入口表达同一概念却行为不同的情况。
- 桌面三栏、窄桌面按需复核、移动三面板都可阅读、可操作、无内容重叠或横向溢出；长标题、路径、代码和状态在不同窗口下不破坏布局。
- 键盘焦点、tab/panel、按钮标签、ARIA 公告、减少动画、浅/深色状态都经过实际验证；语义不单靠颜色表达。
- `npm run verify` 通过；新增或调整行为有针对性测试。视觉验收截图可复现，保存在已忽略的 `test-results/`，并在迭代日志中留有生成方式、路径和逐视口结论。
- 没有未解释的高优先级缺陷、测试失败、控制台错误或已知的行为回归。若存在无法关闭的风险，必须在最终汇报中说明影响、证据和恢复路径，不能宣称完成。
- 提交前检查 git diff，保证改动仅服务此目标；文档与实现同步。执行 subagent 不得自行做最终提交、合并、部署或重启，必须把待提交 diff、验证证据和剩余风险交给主 agent 审核；主 agent 按仓库约束使用中文提交并完成后续发布动作。

## 汇报格式

每轮只汇报高信号事实：

1. 本轮用户体验改善与对应文件。
2. 已运行的验证及结果，包括截图结论。
3. 从评审或自检中发现并已处理的问题。
4. 剩余风险与继续/结束的判断。

最终汇报还应给出：改动概览、测试结果、截图覆盖的视口和生成方式、可复现的手工检查路径，以及供主 agent 审核的待提交文件清单。
```

## 主 Agent 协调规则

1. 先将提示词交给一个拥有 `public/`、相关测试和文档写入权限的执行 subagent；不要并行委派同一前端文件给多个写入 agent。
2. 每轮执行 agent 返回后，主 agent 必须检查 `git diff`、迭代日志、测试输出和截图，独立确认没有破坏数据源隔离、受限诊断和焦点治理。
3. 对于界面质量，主 agent 至少组织一次只读评审，要求评审意见改变改动、测试或验收判断；没有可验证价值的意见不进入下一轮。
4. 只有质量门槛均有证据支撑时，主 agent 才允许执行 agent 结束；否则回传具体缺陷，要求下一轮继续。
