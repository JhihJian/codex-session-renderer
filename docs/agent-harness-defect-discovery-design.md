# Agent Harness 缺陷发现 MVP

## 目标

将历史 Pi 会话中的一个异常现象，转化为一个独立、可执行、可判断的 harness 缺陷。

最终产物不是“会话中出现过错误”的清单，而是一份缺陷列表。列表中的每一项都能回答：在什么最小输入下，harness 违反了什么确定性规则，如何再次运行并观察到它，以及为什么基线行为没有该问题。

## 第一性原理

会话只能说明某次运行发生了什么，不能说明原因。一个真正的 harness 缺陷必须证明以下反事实：

```text
在相同任务、相同输入、相同工具行为和相同配置下，
只改变 harness 版本或被测开关，失败是否出现？
```

因此，MVP 的唯一判断对象是机器可判定的失败谓词 `F`。

示例：

- `F = 取消后工具替身仍被调用`；
- `F = 进入模型上下文的消息与会话规则计算的消息不一致`；
- `F = 同一个 tool call 被执行超过一次`。

“agent 没有完成任务”“输出不够好”“用户再次纠正了 agent”不是 `F`，只能用于找到候选。

## 最小闭环

```text
会话归档
  -> 候选
  -> 断言
  -> 复现包
  -> 被测/基线对照运行
  -> confirmed 或 rejected
  -> 缺陷列表
```

这条链路中的每一步只做一件事。

| 步骤 | 输入 | 输出 | 唯一职责 |
| --- | --- | --- | --- |
| 1. 会话归档 | 原始 Pi JSONL | 可定位的会话快照 | 保留历史事实，不判断缺陷 |
| 2. 候选提取 | 会话快照 | `candidate` | 写清楚异常发生在哪里、观察到什么 |
| 3. 断言定义 | candidate | 失败谓词 `F` | 定义预期行为和实际失败，不可自动判断则停止 |
| 4. 复现包 | `F` 与最小上下文 | 可执行 fixture | 去掉与失败无关的会话内容，固定输入与行为 |
| 5. 对照运行 | fixture | 被测与基线结果 | 除 harness 变量外，运行条件必须相同 |
| 6. 结果登记 | 两组结果 | `confirmed` 或 `rejected` | 只将可对照复现的问题写入缺陷列表 |

## 三项 MVP 能力

### 1. 会话线索簿

会话线索簿是历史会话到候选的最小桥梁。它不需要全量自动检测，也不需要完整重建每个会话的语义。

每条候选只记录：

```yaml
id: C-001
source:
  session: <会话文件或会话 ID>
  event: <原始事件坐标>
observation: 工具调用报错后，后续同一调用再次出现
suspected_rule: 同一 tool call 只能执行一次
status: candidate
```

候选可以由人工在现有会话工作台中选择。MVP 不要求自动找出所有候选，也不要求给候选打严重性分数。

### 2. 最小复现执行器

复现执行器在新的临时工作目录中运行 Pi。它不读取原会话，不进入真实项目目录，只使用复现包提供的内容。

复现包固定四样东西：

1. 最小任务输入；
2. 固定的 provider 响应；
3. 必要的工具替身及其返回值；
4. 被测 harness 版本或配置，以及基线版本或配置。

脚本化 provider 与工具替身的目的是让 agent 的行为成为输入，而不是变量。执行器输出：实际事件顺序、工具调用记录、最终状态和 `F` 的判断结果。

最小复现包可从一个结构化文件开始：

```yaml
id: H-001
input: "执行任务"
provider_script: provider.json
tool_script: tools.mjs
predicate:
  id: no_tool_execution_after_cancel
  type: event_count
  eventType: tool_execution_end
  expected: 0
baseline:
  pi: <基线版本或配置>
candidate:
  pi: <被测版本或配置>
runtime:
  kind: pi
  candidate: { command: <候选 Pi 命令> }
  baseline: { command: <基线 Pi 命令> }
expected: 工具调用次数为 0
```

### 3. 缺陷登记簿

缺陷登记簿只有三种状态：

- `candidate`：历史会话显示异常，但尚未完成复现；
- `confirmed`：被测 harness 触发 `F`，基线不触发；
- `rejected`：无法形成自动断言，或两组结果没有差异。

`confirmed` 条目必须包含：

```yaml
id: H-001
title: 取消后仍执行工具调用
predicate: no_tool_execution_after_cancel
fixture: fixtures/H-001
command: <执行复现的命令>
expected: 工具调用次数为 0
actual: 被测 harness 调用 1 次，基线调用 0 次
candidate: C-001
versions: <被测与基线版本/配置>
status: confirmed
```

修复版本、外部 issue、严重性、统计报表和完整回归平台均不是确认缺陷的前置条件。

## 确认规则

一个候选成为 `confirmed`，必须满足：

1. 有一个明确、自动可判断的失败谓词 `F`；
2. 有独立的最小复现包；
3. 被测 harness 在复现包中触发 `F`；
4. 基线在同一复现包中不触发 `F`；
5. 连续运行三次，结果一致；
6. 缺陷条目包含运行命令、fixture、预期、实际和来源候选。

基线可以是修复版本、旧版本，或同一 harness 中代表正确行为的配置。关键不在基线的形式，而在两组运行只改变被验证的 harness 因素。

以下情况直接得到 `rejected`：无法把异常写成 `F`、无法构造独立复现包、基线同样失败，或重复运行的结果不一致。

## MVP 工作方式

先选一个确定性、机械性强的会话线索作为首个样本。适合的线索通常涉及消息投影、工具调用配对、取消、重试或重复执行，因为它们可以由固定输入和断言验证。

一次只处理一个候选，并完成完整闭环：

```text
选择历史线索
-> 写出 F
-> 做最小 fixture
-> 跑被测和基线
-> 登记 confirmed/rejected
```

首个闭环完成后，再根据已经出现的重复工作决定是否增加自动候选检测、通用会话投影器、更多类型的复现器或更复杂的实验体系。

## 非目标

MVP 不处理：

- 从全部会话自动发现全部问题；
- 复杂分支、压缩、并发和概率性问题；
- 多模型、多项目、多扩展的实验矩阵；
- 缺陷严重性、修复流程和外部 issue 同步；
- 完整的长期回归平台。

这些能力只有在首个确定性缺陷闭环已经跑通，且真实重复需求出现后才有价值。

## 设计验收

MVP 成立的标志不是已分析多少会话，而是至少有一个历史会话线索被清楚地登记为以下两者之一：

- `confirmed`：任何人都能在新临时目录执行同一命令，观察到被测与基线对 `F` 的稳定差异；
- `rejected`：有证据表明它只是历史异常，不能证明是 harness 缺陷。
