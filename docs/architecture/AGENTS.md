# 架构文档

本目录保存项目当前架构的正式说明。它帮助工程师在修改前理解系统目的、边界、责任、关键流程和必须保持的规则。

## 文档边界

- 架构总览由 `.agents/architecture/state.json` 中 `overview` 角色指定，说明系统目的、稳定边界、主要模块、阅读路径和必须保持的规则。首次建立时可以复用项目已有架构入口。
- `modules/<名称>.md` 先提供可独立审阅的设计层，再说明模块的责任、拥有的数据或状态、依赖、失败处理和扩展边界。实现细节不能遮蔽设计结论、资源关系、模块交互和规则。
- 跨模块流程写在总览或专门流程文档中，并链接到相关模块说明。
- 可枚举的接口、字段、配置、事件、状态和源码映射写在实现参考或源码契约中。
- 只有空间关系、顺序、状态、责任转移或边界穿越确实更适合图形表达时才制图，图表规则见[架构图编写协议](../../.agents/skills/references/diagram-authoring.md)。
- 重要选择的原因、备选方案和代价写入项目已有的决定负责位置，不在这里重复；已安装决定治理时由对应 Agent Note 负责。

总览不写字段、接口参数、完整配置、算法步骤或测试步骤。代码、配置和测试能够直接说明的细节放在模块文档、参考文档或源码中。

架构文档按“事实底稿、实现参考、模块设计、架构总览”逐级精炼。事实底稿只作为生成依据；模块设计从实现事实中抽象职责、所有权、依赖和失败语义；总览只能从已确认的模块结论提炼稳定目的、边界、核心流程和长期业务约束。没有独立读者价值的段落、能力、保证或流程不得为了满足结构而创建。详细执行规则见[分层架构文档写作协议](../../.agents/skills/references/layered-authoring.md)。

## 长期业务约束

架构总览使用“长期业务约束”作为顶层规则章节。该章节只收录目标项目领域特有、预计跨越多个需求版本仍然成立，并且在违反后会改变核心业务结果或领域对象语义的规则。规则必须由当前代码、有效测试或已确认的业务资料证明，并能够用业务语言表达。

以下内容不得进入“长期业务约束”：事实所有权、模块自治、跨模块幂等等通用架构原则；事务、消息、重试、租约、锁、缓存等实现机制；哈希、对象版本、超时和容量限制等校验细节；通用认证授权、部署前置条件和运维门禁；接口字段、Schema、SQL、配置项和测试步骤。没有符合条件的规则时，省略该章节。

一项要求只在一个位置完整说明：长期业务约束由架构总览负责，模块规则由 `modules/<名称>.md` 负责，跨模块阶段和失败边界由总览或流程文档负责，精确实现事实由实现参考、README、专题文档或源码契约负责，决策原因由项目的决定负责位置承担。其他位置只保留短摘要和链接。状态记录是证据账本，不是架构正文；账本中的 `guarantee` 结论不能直接等同于顶层长期业务约束，只有明确归属于架构总览的已确认业务结论才能写入该章节。

## 模块设计的审阅优先级

模块设计首先服务于需求和设计审阅，其次才服务于实现定位。读者不应依赖源码、配置、字段、接口或数据库结构，才能判断一个设计是否解决问题、边界是否合理、职责是否清楚，以及能否与现有模块协作。

新建模块文档，或对既有模块进行实质性重构时，正文先建立审阅层。`设计结论` 必须位于开头，其余内容按项目适用性和读者问题选择，不创建空章节：

1. `设计结论`：说明采用什么设计，以及设计解决的核心问题。
2. `要解决的问题`：说明当前缺口、风险或新增需求。
3. `核心模型`：说明主体、资源、关系、状态或权限如何组织。
4. `与现有模块的交互`：说明本模块提供什么判断或能力，依赖谁，以及其他模块继续拥有的责任。
5. `必须保持的规则`：列出不可被实现细节改变的边界、不变量和安全约束。
6. `交付边界`：说明首版覆盖什么、明确不覆盖什么，以及仍待确认的外部事实。

审阅层必须位于实现定位之前。类名、包路径、接口参数、配置字段、SQL、表字段、迁移步骤、异常码、算法步骤和测试清单不得成为审阅层的主体；它们分别下沉到实现参考、专题文档、Schema、SQL、测试或项目已有的决定负责位置。

目标设计必须在开头明确标注尚未实现，当前事实、已确认推断和目标设计不得混写。既有模块文档不要求一次性改写；仅在新建或实质性调整时按本结构演进。

完成模块设计后，先不阅读源码，只阅读标题、设计结论、核心模型、模块交互、规则和交付边界，检查能否回答：

- 该设计解决什么业务或系统问题。
- 哪些主体能对哪些资源做什么。
- 数据、权限或状态从哪里继承，边界在哪里。
- 本模块与现有模块如何协作，哪些责任没有被它接管。
- 哪些规则不能因后续实现而被放宽。
- 首版有意不做什么，哪些事实仍待确认。

任一问题无法明确回答时，应先重组审阅层，而不是继续补充实现细节。

## 合格要求

架构文档必须说明项目目的、系统边界和主要模块。关键规则、用户能力和跨模块流程按项目适用性建立；不适用时省略正文，并在状态账本中保留判断依据。涉及数据责任、外部系统或权限时，必须说明负责方、边界和失败后果；确实不适用时写明原因和依据。

每项能力写清参与者、结果、前提和失败路径。每项关键规则写清适用范围、违反后果、负责模块、实现位置和验证位置。每个结论在 `.agents/architecture/state.json` 中保留文档位置、依据和必要的测试位置。

## 依据与待确认事项

代码、配置、有效测试、运行资料和已生效决定可以支持当前事实。旧文档、目录名、`import`、函数名和单次测试结果只能帮助调查，不能单独写成当前事实。

无法确认的内容写为待确认事项，说明影响、还需要的资料和下一次检查位置。尚未实现的需求写为声明目标。关键冲突、权限、数据、外部接口或主流程缺少依据时，架构不得生效。

## 使用方式

首次建立先使用 [调查架构](../../.agents/skills/investigate-project-architecture/SKILL.md)，再使用 [生成架构](../../.agents/skills/generate-project-architecture/SKILL.md)。代码变更后使用 [维护架构](../../.agents/skills/maintain-project-architecture/SKILL.md)。只读检查使用 [检查架构](../../.agents/skills/check-project-architecture/SKILL.md)，旧资料迁移使用 [迁移架构](../../.agents/skills/migrate-project-architecture/SKILL.md)。
