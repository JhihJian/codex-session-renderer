# 架构图编写协议

本协议约束架构文档中的关系图、流程图、时序图、数据流图、生命周期图和信任边界图。它不要求项目生成固定数量的图，也不要求采用固定物理目录。

## 使用门槛

只有在空间关系、顺序、状态变化、责任转移或边界穿越比文字或表格更容易扫描时才画图。每张图必须帮助读者完成一个明确的理解、修改、故障定位或安全判断任务。

一图一问：每张图只回答一个明确问题。

删掉图后，如果读者不会失去具体判断能力，就删除图或改用文字、列表和表格。不要为了满足“架构完整”而生成图。

## 图类型和位置

| 图类型 | 主要问题 | 推荐位置 |
| --- | --- | --- |
| 系统上下文图 | 系统服务谁、依赖谁、边界在哪里 | 架构总览 |
| 核心场景时序图 | 一次关键请求经过哪些责任方，哪里失败 | 架构总览或流程文档 |
| 模块责任图 | 谁负责什么，依赖方向和修改入口是什么 | 架构总览或模块设计 |
| 数据责任图 | 数据由谁创建、拥有、修改和持久化 | 模块设计或数据文档 |
| 实体生命周期图 | 有哪些稳定状态，谁触发转换，哪些转换非法 | 模块设计或流程文档 |
| 信任边界图 | 身份在哪里确认，凭据如何流动，哪些操作受限 | 架构总览或安全文档 |
| 运行时组成图 | 启动后有哪些运行单元以及如何连接 | 运行时或部署文档 |

默认优先生成一张系统上下文图和一张最关键场景图。数据、状态、权限或运行时关系只有在确实增加判断价值时再分别制图。实现参考可以维护可检索的接口、事件或调用关系，但不把这些全集作为顶层架构图。

## 视图拆分与图组

先写每张图要帮助谁回答什么问题，再选择图型。三张图是常见的新人入门组合，但不是固定模板；没有独立读者价值的视图不应为了完整性创建。

| 读者问题 | 推荐视图 | 保留内容 | 明确下沉内容 |
| --- | --- | --- | --- |
| 系统服务谁、依赖谁、边界在哪里 | 系统上下文图 | 使用者、外部系统、在线服务、基础设施类别和主要交互 | 内部模块、类、接口字段、部署实例 |
| 一次业务如何从触发走到结果 | 业务流程图或场景时序图 | 业务阶段、责任转移、主要结果和关键异步边界 | 方法调用、重试参数和完整异常分支 |
| 核心对象如何关联、谁拥有谁 | 对象关系图或数据责任图 | 核心对象、数据血缘、所有权和生命周期关系 | 普通字段、索引、SQL 和完整 Schema |
| 一个对象有哪些状态、哪些转换合法 | 实体生命周期图 | 稳定状态、迁移、守卫、终态和失败出口 | 页面流程、数据库实现和完整事件字段 |
| 请求、响应和事件按什么顺序发生 | 核心场景时序图 | 关键参与者、请求、响应、异步分支和责任交接 | 领域对象全集、算法和日志细节 |
| 系统运行在哪些节点和网络区 | 运行时组成图 | 服务实例、网络边界、运行依赖和协议方向 | 业务对象和详细业务流程 |

图组应提供建议阅读顺序。面向新人的常见顺序是“系统上下文 → 核心业务流程 → 核心对象关系”，面向排障的图组可以改为“系统上下文 → 部署拓扑 → 关键时序”。每张图必须明确它没有回答的问题，避免读者将省略理解为不存在。

## 信息密度与拆分

节点数量只是复核信号，不是硬性上限。5 至 9 个主要节点通常适合第一版，超过 12 个节点时必须检查是否能够按读者问题拆分；如果确实不能拆分，应记录保留全图的理由。

出现以下任一情况时优先拆图：

- 同一张图同时表达系统边界、模块依赖、请求时序、对象关系或部署拓扑。
- 同一条连线既表示同步调用，又表示异步事件或静态依赖。
- 主阅读方向超过两个，读者需要来回追踪交叉线。
- 图例需要解释三种以上没有直接文字标签的颜色或线型。
- 节点必须放入长段文字，或正常文档宽度下需要频繁缩放。

拆分后，每张图仍须独立回答一个问题，并通过稳定名称、元素身份和图外链接保持关联。不要通过复制全部节点和连线制造多张“看似拆分、实际重复”的图。

## 图组契约

复杂图组在图前、图后或相邻的结构化记录中保留以下契约：

```text
图组：建议阅读顺序和整体目标
图 ID：稳定的语义身份，不使用布局位置命名
问题：本图回答的唯一主要问题
范围：本图覆盖的系统、模块、对象或阶段
不表达：本图有意下沉的内容
状态：当前实现、目标设计、对比或待确认
事实所有者：节点和关系对应的唯一负责模块或文档
证据：架构结论、源码、配置、测试、运行资料或决定记录
维护方式：curated、generated 或 hybrid generated
下钻：模块设计、实现参考、专题文档或决定记录
```

同一图组中的角色、系统、模块、对象、基础设施和关键关系应使用稳定 ID。显示名称可以因视图缩短，但必须保留别名映射，不能因为换图而创建同义节点。

当前实现和目标设计必须用不同图、明确分区或直接标签区分。不能只通过浅色、虚线或排列位置让读者猜测状态。

## 分层边界

- 总览图只表达系统边界、主要责任单元和关键跨模块关系。
- 模块图表达局部责任、数据所有权、依赖、状态和失败传播。
- 实现参考可以表达接口、字段、配置、事件、类型和调用链。
- 不在一张图中混合系统边界、模块依赖、请求时序、字段结构和部署拓扑。
- 节点优先使用责任单元名称，例如“授权模块”“任务协调器”“状态存储”，不要使用文件名和函数名代替架构节点。
- 图组可以跨层渐进披露，但单张图不能混合系统边界、模块依赖、请求时序、字段结构和部署拓扑。

## 图契约

每张图必须在图前或图后声明：

```text
问题：一次外部请求失败时，哪个模块负责拒绝、重试和记录？
范围：只覆盖请求入口、授权、任务协调和状态存储。
不表达：函数调用顺序、字段全集和内部算法。
边语义：实线表示同步调用，虚线表示异步消息，箭头表示控制或数据方向。
维护方式：curated；依据代码入口、状态定义和失败测试维护。
下钻：链接到对应模块设计和实现参考。
```

每条关键边都使用明确动词，例如“调用”“发布事件”“读取权威状态”“转换数据”“验证身份”或“持久化”。颜色、形状、线型和分组必须有图例；颜色不能成为唯一语义。已确认、推断、声明目标、冲突和未知不能使用相同样式表达。

## 证据和维护

每个关键节点和关系都必须能追溯到代码、配置、有效测试、运行资料或已生效决定，并有唯一负责文档。代码存在调用关系只能证明调用，不自动证明业务流程、数据所有权或信任边界。`curated` 图也不能脱离证据编造关系。

可枚举图使用 `generated` 或 `hybrid generated` 时，必须说明权威来源、发现集合、分类映射、显式豁免和检查方式。生成结果应稳定排序、可重复重建并能检查陈旧。无法闭合的事实进入风险视图，不伪装成完整图。
- 不能只检查证据路径存在。还要判断来源是否真正支持该节点或关系、描述的是当前态还是目标态，以及关系方向是否与证据一致。
- 代码、配置、测试、外部边界或架构文档改变后，受影响的图必须重新检查节点、关系、边界、所有权、契约和下钻链接。未复核的图不能继续宣称当前架构。

## 清晰度验收

1. 一句话问题测试：读者能否说清这张图回答什么问题。
2. 范围测试：读者能否看出图覆盖和有意不覆盖的内容。
3. 边语义测试：每条关键边的方向、动作、同步性和条件是否明确。
4. 反事实测试：删掉一条关键边后，读者能否说出哪个修改、故障或安全判断会改变。
5. 读者任务测试：陌生工程师能否在三分钟内找到责任模块、修改入口、失败点和下钻文档。
6. 展示测试：实际渲染后标题、节点、箭头和图例可读；缩放、窄屏、黑白或无法渲染时仍有正文说明或表格替代。
7. 图组一致性测试：跨图名称、稳定 ID、边界、所有权、关系方向、当前/目标状态和术语是否一致。
8. 认知负担测试：图是否只保留一个主问题，节点和连线是否处于可读预算内，省略内容是否有负责位置。

节点、边或图例需要长篇解释时，优先拆成多张一问一答的图。规模不是绝对门槛，但一张图不得成为全量目录、全量调用链或全量事件清单。

## 常见错误

以下内容通常应下沉到实现参考或删除：

- `index.ts -> parseInput() -> normalizeOptions()` 形式的函数调用链。
- 将所有模块、接口、事件、配置和部署节点塞进一张全景图。
- 只用无标签箭头表达“模块 A 连接模块 B”。
- 把目录结构、函数名称或普通 `import` 直接解释成架构关系。
- 用“暂无内容”“后续补充”等文字为图预留结构。
