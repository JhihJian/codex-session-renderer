# 分层架构文档写作协议

本协议是架构文档生成、维护和检查 Skill 的共同详细规则。它不要求项目新增固定目录，逻辑层级应映射到项目已有的架构总览、模块说明、参考文档、源码契约和决定负责位置。

图表的选择、分层、证据和可读性遵循[架构图编写协议](diagram-authoring.md)。

## 目标

架构文档帮助陌生工程师理解系统、定位修改入口并识别不能破坏的规则。它不是源码目录的扩写，也不是接口、配置和测试的全集。

## 四级产物

生成顺序固定为“事实底稿 -> 实现参考 -> 模块设计 -> 架构总览”。事实底稿是生成过程材料，不直接作为读者文档；其余三层承担不同职责：

| 层级 | 必须回答 | 不承载 |
| --- | --- | --- |
| 实现参考 | 当前有哪些接口、字段、配置、类型、事件、状态、源码入口和测试映射 | 系统整体目的、模块取舍和跨模块解释 |
| 模块设计 | 模块解决什么问题、采用什么核心模型、负责什么、拥有何种数据或状态、依赖谁、如何失败、如何扩展、不负责什么 | 完整接口、配置、算法和逐文件调用链 |
| 架构总览 | 系统是什么、边界在哪里、主要责任单元如何协作、核心流程和长期业务约束是什么 | 字段、参数、配置全集、算法步骤、事件全集和测试步骤 |

设计理由和备选方案进入项目负责该决定的位置，不在总览或模块文档中重复；已安装决定治理时由对应 Agent Note 负责。

## 逐级精炼

1. 事实底稿只写证据支持的当前事实，并标记 `confirmed`、`inferred`、`declared-target`、`conflict` 或 `unknown`。
2. 实现参考完整记录可以枚举的事实，不把函数名、目录名或单次测试结果提升为设计意图。
3. 模块设计从实现事实中抽象稳定职责、边界、所有权、依赖和失败语义。
4. 架构总览只能从已确认的模块结论中提炼，不得直接从源码向总览添加实现细节。总览中的长期业务约束必须按照项目 `docs/architecture/AGENTS.md` 判定，不能把状态账本中的 `guarantee` 全量渲染为顶层规则。
5. 每层只回答本层读者的问题。需要下钻时使用链接，不在上层复制下层全文。

## 模块设计的读者审阅

模块设计在进入实现定位前，必须先满足项目 `docs/architecture/AGENTS.md` 定义的审阅结构和读者检查。该项目规则是固定章节及验收问题的唯一来源；本协议只要求先让读者判断设计是否覆盖问题、主体和资源关系、模块责任、关键规则及交付边界，再下钻实现细节。

审阅时先忽略源码定位、接口、配置、字段、SQL、迁移和测试清单。若读者无法不依赖这些细节说明模块解决的问题、与现有模块的关系和不可放宽的规则，应先重组模块设计，不以增加实现信息作为修复方式。

## 最小充分原则

没有独立读者问题、稳定边界、责任、长期业务约束、流程、失败后果或下钻价值的段落必须删除。不能为了满足固定章节、条目类型或文档长度而创建内容；没有合格长期业务约束时省略该章节。

以下内容直接省略或下沉：

- “本章将介绍”“后续补充”“暂无内容”等占位文字。
- 没有证据的质量、扩展性或可靠性宣称。
- 逐文件目录、完整调用链、接口参数、字段清单和配置全集。
- 已由其他负责文件完整说明的事实。

精简不得删除行为主体、前置条件、时序、强制程度、例外、所有权、失败方式或失败后果。

## 适用性和不确定性

能力、长期业务约束和跨模块流程只有在项目确实具有该内容且有证据时才建立。不适用内容省略，不能用普通段落伪装成条目。重要但无法确认的内容进入待确认事项；冲突、未知和声明目标不得写成当前架构事实或无条件晋升为生效基线。

## 归属和追溯

每条事实只有一个完整负责位置。总览结论必须能追溯到模块设计，长期业务约束的完整规则只由总览负责；模块结论必须能追溯到事实底稿和实现参考，事实必须有可定位证据。其他位置只保留短摘要和链接。

## 章节验收

完成每层后分别检查：

- 只看标题和开头，目标读者能否完成该层的主要任务。
- 是否出现上一层或下一层的完整内容。
- 是否存在没有读者价值的段落或为了凑结构产生的条目。
- 关键条件、责任、失败后果和限制是否仍然完整。
- 每条结论是否只有一个负责位置并能向下追溯。
